# M5.1 Release Reliability Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the unsupported v0.1.0 one-install Skill ZIP with an official multi-Skill Plugin artifact, make release provenance fail closed against actual Git state, remove the broken legacy shim from current artifacts, add executable pressure-eval contracts, and surface repository-governance status without claiming protection that is not enabled.

**Architecture:** Keep `.agents/skills/*` as canonical repository sources. `package_release.py` materializes two distributions from those sources: an official Plugin layout and the existing Codex bundle. Provenance is derived from verified Git state. Deterministic CI validates packaging and eval contracts; real-agent results and live branch protection remain explicit release gates rather than simulated evidence.

**Tech Stack:** Python 3.12, Git, deterministic ZIP helpers, JSON contracts, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-27-m5.1-release-reliability-design.md`

## Global Constraints

- Preserve M0–M4 runtime architecture and all current regression tests.
- `$amazon-japan-creative-workflow` remains the only normal user-facing invocation.
- Current Plugin bundle uses `.codex-plugin/plugin.json` plus `skills/` and must not use `internal-skills/` discovery.
- `japan-listing-demo`, `listing-hardening`, and `validate_project_state.py` remain repository compatibility source but are excluded from current release artifacts.
- Release provenance must derive from verified Git state; caller-declared SHA alone is never authoritative.
- Deterministic CI must not claim that textual eval fixtures are real-agent evidence.
- No automatic merge or v0.1.1 publication.

### Task 3: Git-derived provenance

**Files:**
- Modify: `scripts/package_release.py`
- Modify: `scripts/selftest_release_packaging.py`
- Modify: `docs/release.md`

**Interfaces:**
- Produces: `verify_git_source(expected_commit: str | None) -> str` returning the authoritative HEAD SHA.

- [ ] **Step 1: Implement Git checks**

The builder must execute:

```bash
git rev-parse --verify HEAD
git status --porcelain --untracked-files=no
```

Fail if Git is unavailable, HEAD is not a full 40-hex SHA, tracked state is dirty, or `expected_commit` differs from HEAD.

- [ ] **Step 2: Derive manifest provenance**

`build_release()` records only the SHA returned by `verify_git_source()`. Caller input is a constraint, not the source of truth.

- [ ] **Step 3: Prove negative cases**

Tests create a temporary Git repository with one committed fixture and assert:

```text
correct HEAD + clean tree -> PASS
fake expected SHA -> FAIL
dirty tracked file -> FAIL
```

- [ ] **Step 4: Document exact meaning**

Change documentation from “declared source commit” to “verified current Git HEAD of a clean tracked tree.”
