# M5.1 Release Reliability Hardening Design

## Status

Approved direction from the 2026-08-27 post-release audit. M0–M4 business architecture remains unchanged. M5.1 only repairs distribution, provenance, runtime packaging, agent-eval readiness, and repository governance gaps exposed after v0.1.0.

## Problem statement

v0.1.0 proved deterministic packaging under its own contract, but that contract was incomplete in five ways:

1. the one-install `.skill.zip` embedded downstream Skills under `internal-skills/`, which is not an OpenAI Plugin discovery layout;
2. `--source-commit` accepted any 40-hex string and did not bind the artifact to the actual Git tree being packaged;
3. the one-install artifact carried `validate_project_state.py`, whose `listing-hardening` dependency was excluded from the artifact;
4. deterministic tests did not execute real agent pressure scenarios;
5. `main` was unprotected and CI success was advisory rather than an enforced merge condition.

## External distribution contract

OpenAI's current Plugin documentation defines a plugin as the installable package that can group related Skills. A plugin has `.codex-plugin/plugin.json`, and bundled Skills live under a plugin-root `skills/` directory referenced by `"skills": "./skills/"`.

M5.1 therefore deprecates the v0.1.0 one-install Skill ZIP as a supported installation path. The supported distribution forms become:

- **Plugin bundle** — installable multi-Skill package using `.codex-plugin/plugin.json` + `skills/<skill-name>/...`;
- **Codex bundle** — repository/project distribution preserving `.agents/skills/<skill-name>/...` for repo-scoped use;
- **repository checkout** — development/source-of-truth path.

The user-facing workflow name remains `$amazon-japan-creative-workflow`.

`plugin.json` must point to `./skills/` and use the same semantic version as `VERSION` and the router manifest. No `internal-skills/` discovery convention is permitted in current artifacts.

## Exact provenance contract

Release artifacts must be bound to the Git content actually packaged, not to a caller declaration.

### Repository mode

When `package_release.py` builds from the current checkout:

- `git rev-parse HEAD` must succeed;
- the working tree and index must be clean for release-relevant tracked files;
- an explicitly supplied `--source-commit` must equal `HEAD`;
- the source commit written to `BUILD_INFO.json` and the release manifest is derived from verified Git state, not trusted caller text.

### Commit-tree mode

For publication automation, the builder may operate from an exact checked-out commit. The workflow must checkout the approved full SHA, verify `HEAD == approved SHA`, and build from that clean tree.

Negative tests must prove that fake SHA, wrong HEAD, and dirty tracked content fail closed.

## Runtime cleanup

`amazon-japan-creative-workflow/scripts/validate_project_state.py` is legacy compatibility code whose dependency is intentionally not part of current distribution. M5.1 excludes it from Plugin and Codex release artifacts. Repository source remains untouched unless a later compatibility milestone explicitly migrates it.

The release validator must fail if this shim leaks into either current artifact.

## Agent pressure-eval contract

M5.1 adds 10 executable pressure-eval cases as release readiness evidence:

1. clear `继续` advances only when the current stage contract is complete;
2. `这张先过` locks only the current Asset candidate;
3. `先这样` does not advance a major stage;
4. missing evidence remains unresolved and is not invented;
5. a Strategy gap discovered during production routes to Stage 0–7 and preserves unaffected approvals;
6. Set QA failure reopens only diagnosed assets;
7. Simulator Pending remains reviewable but blocks Final;
8. Final eligibility with missing semantic/runtime evidence remains `UNVERIFIED`;
9. long-context noise does not change stage ownership or user-facing entry point;
10. one Golden Path crosses Strategy → Production → Quality → Simulator → Hardening without manual invocation of internal Skills.

The repository must contain both the case manifest and a runner contract. Deterministic CI validates the case definitions and expected structured assertions. A **real-model run is a separate release gate** and must produce a machine-readable result artifact; deterministic CI must not pretend that textual fixtures are equivalent to real agent execution.

## Repository governance

Desired production rule for `main`:

- merge through PR;
- require the M5.1 validation workflow to pass before merge;
- prohibit direct pushes except an explicitly documented break-glass path;
- require at least one approval when the hosting plan/settings support it.

Because repository administration APIs are not exposed by the current ChatGPT GitHub connector, M5.1 will add a machine-readable `docs/main-protection-required.md` and a CI/governance checker that reports the live GitHub state. The code milestone is not allowed to claim branch protection is enabled until the API reports it.

## v0.1.0 disposition

v0.1.0 remains an immutable historical release. Documentation for v0.1.1 must explicitly state:

- v0.1.0 `.skill.zip` is deprecated and unsupported for multi-Skill installation;
- the v0.1.0 Codex bundle/repository checkout may still be used for pilot work subject to the provenance caveat;
- v0.1.1 supersedes v0.1.0 for installation once M5.1 is merged, real-agent evals are executed, and governance status is reviewed.

## Release gate

M5.1 code may merge only after deterministic CI is green. A formal v0.1.1 release additionally requires:

- Plugin artifact validates and contains the official plugin manifest layout;
- Codex bundle validates;
- exact Git provenance negative tests pass;
- legacy shim is absent from current artifacts;
- real-agent pressure eval result is present and passing;
- `main` protection/ruleset state is explicitly checked and recorded;
- user explicitly approves publication.
